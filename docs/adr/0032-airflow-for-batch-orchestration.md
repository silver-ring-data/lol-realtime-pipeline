# 0032. 배치 파이프라인 오케스트레이션 도구 선정: Airflow vs Lambda

> 원본: https://app.notion.com/p/3511198df8d980c88c84c57d13d4f6c5

| 상태 | 날짜 |
|---|---|
| 채택 | 2026-04-30 |

## 현상

- 현재 파이프라인은 Flink를 통해 실시간 지표(응원 화력 등)를 산출하고 있음.
- 하지만 경기 종료 후 수행되는 **실버 데이터 정제(Glue Job)** 및 **최종 리포트 생성(Athena)** 작업은 초 단위의 실시간성이 요구되지 않음.
- 초기에는 'EventBridge + Lambda'를 활용한 릴레이 방식을 고려했으나, 작업 간의 의존성 관리와 실패 시 재실행(Retry)의 복잡성 문제가 제기됨.

## 결정

- 실시간성이 낮은 **사후 분석 및 배치 가공 작업**에는 **Apache Airflow**를 전용 오케스트레이터로 사용하기로 결정함.
- 실시간 트랙(Speed Layer)과 배치 트랙(Batch Layer)의 도구를 명확히 분리함.

## 이유

1. **워크플로우 가시성 (Observability):** 람다 릴레이 방식은 흐름이 파편화되어 한눈에 파악하기 힘듦. Airflow의 DAG 그래프를 통해 `S3 감시 -> Glue 실행 -> Athena 분석` 과정을 직관적으로 관리할 수 있음.
2. **장애 대응 및 재실행 (Error Handling):** 특정 단계(예: Glue Job)에서 실패했을 때, Airflow UI를 통해 실패 지점부터 즉시 재실행이 가능하며 `retries` 설정을 통해 자동 복구가 용이함.
3. **적재적소의 도구 활용:** 1초가 급한 작업은 '이벤트 기반(Lambda)'으로, 안정성과 순서가 중요한 작업은 '지휘자(Airflow)'에게 맡김으로써 시스템 전체의 정합성을 높임.
4. **비용 효율성:** 분석 작업이 끝날 때까지 람다를 계속 띄워놓거나 복잡한 상태 체크 로직을 짜는 것보다, 배치 전용 도구를 쓰는 것이 운영 관리 면에서 더 경제적임.

## 트레이드오프

### 4. 결과 및 영향 (Consequences)

- **장점:** 파이프라인 관리가 심플해지고, 분석 결과에 오류가 있을 경우 과거 데이터 재처리(Backfill)가 매우 쉬워짐.
- **단점:** Airflow 서버를 유지하기 위한 추가적인 인프라 리소스가 필요함.
- **추후 계획:** Airflow의 `S3KeySensor`를 활용해 봇이 올리는 `finish.json` 신호를 감지하는 즉시 배치 잡이 시작되도록 DAG를 구현할 예정.

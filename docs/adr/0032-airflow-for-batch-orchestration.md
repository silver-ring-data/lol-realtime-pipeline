# 0032. 배치 파이프라인 오케스트레이션 도구로 Airflow 를 선정한다 (vs Lambda)

## 배경

Flink 로 실시간 지표(응원 화력 등)를 산출하고 있지만, 경기 종료 후 수행하는 실버 데이터 정제(Glue Job)와 최종 리포트 생성(Athena)은 초 단위 실시간성이 필요 없다. 초기에는 EventBridge + Lambda 릴레이를 고려했으나, 작업 간 의존성 관리와 실패 시 재실행(Retry)의 복잡성 문제가 제기되었다.

## 선택지

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. Apache Airflow 를 배치 전용 오케스트레이터로 사용 | DAG 가시성, 실패 지점부터 재실행, `retries` 자동 복구, Backfill 용이 | Airflow 서버 유지 인프라 필요 |
| B. EventBridge + Lambda 릴레이 | 서버리스 | 흐름 파편화, 상태 체크 로직 복잡 |

## 결정

**A 를 채택한다.** 실시간 트랙(Speed Layer)과 배치 트랙(Batch Layer)의 도구를 명확히 분리한다. 1초가 급한 작업은 이벤트 기반(Lambda), 안정성과 순서가 중요한 작업은 Airflow 에 맡긴다. 추후 `S3KeySensor` 로 봇이 올리는 `finish.json` 신호를 감지하는 즉시 배치 잡이 시작되도록 DAG 를 구현한다.

## 결과

- 좋아지는 것: `S3 감시 → Glue 실행 → Athena 분석` 과정을 직관적으로 관리하고, 분석 오류 시 과거 데이터 재처리가 쉽다.
- 감수하는 것: Airflow 서버 유지 리소스.
- 다시 볼 조건: 배치 작업이 단순해져 Airflow 가 과한 도구가 될 때.

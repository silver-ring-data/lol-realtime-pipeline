# 0029. 아키텍처 최적화: RDS 제거 및 OpenSearch 단일 서빙 채택

> 원본: https://app.notion.com/p/3501198df8d980149c5fce27488f4f67

| 상태 | 날짜 |
|---|---|
| 채택 | 2026-04-28 |

## 현상

- 초기 메달리온 아키텍처 설계에서는 실시간 서빙 레이어를 두 개로 분리하여 기획함.
  - **Silver 데이터 (비정형 채팅):** 텍스트 검색에 특화된 OpenSearch
  - **Gold 데이터 (시계열 점수):** 정확한 수치 조회에 특화된 RDS (PostgreSQL)
- 하지만 인프라를 세팅하는 과정에서, 현재 MVP 모델에는 '회원가입', '결제' 등 복잡한 트랜잭션(ACID)을 요구하는 관계형 데이터가 없음을 인지함.
- 단순 시계열 데이터(시간대별 하이라이트 점수) 조회를 위해 RDS를 별도로 유지하는 것은 오버 엔지니어링(인프라 비용 증가 및 관리 복잡도 상승)이라는 문제가 제기됨.

## 결정

- **PostgreSQL(RDS) 도입을 전면 취소**하고, **OpenSearch를 단일 통합 서빙 DB로 격상**시킨다.
- Flink에서 산출된 Silver(정제된 채팅)와 Gold(하이라이트 점수) 데이터를 모두 OpenSearch 인덱스에 적재한다.

## 이유

- **비용 및 인프라 최적화 (Lean & Mean):** 불필요한 RDS 인스턴스(VPC, 서브넷 등)를 제거하여 AWS 클라우드 유지 비용을 획기적으로 절감함.
- **OpenSearch의 성능 활용:** OpenSearch는 역색인(Inverted Index) 기반으로 밀리초(ms) 단위의 초고속 조회가 가능하므로, 시계열 그래프용 데이터를 프론트엔드에 서빙하기에 성능적으로 완벽히 부합함.
- **선택과 집중:** RDS 세팅에 소모될 리소스(시간)를 아껴서, 인프라 자동화(AWS CDK)와 **OpenSearch Dashboards 고도화** 등 프로젝트의 핵심 가치를 높이는 곳에 재투자함.

## 트레이드오프

- 파이프라인이 `[Kinesis → Flink → OpenSearch + S3]` 형태로 매우 간결하고 탄탄해짐.
- API 서버(FastAPI) 구축 시, SQL(`SELECT`) 대신 OpenSearch DSL 쿼리를 작성하여 데이터를 조회하도록 개발 방향 변경.
- 절약된 시간을 활용해 향후 Amazon Bedrock(AI 요약) 연동에 집중할 수 있는 환경 마련.

# 0036. 실시간 리플레이 시뮬레이션을 위한 이종 스트림 시간 동기화

> 원본: https://app.notion.com/p/3531198df8d98076a8d4fce283ca4526

| 상태 | 날짜 |
|---|---|
| 채택 | 2026-05-02 |

## 현상

우리 시스템은 과거의 인게임 이벤트와 현재 시뮬레이션되는 채팅 데이터를 실시간으로 결합해야 한다. 하지만 데이터마다 시간 기준이 달랐다:

- **인게임 데이터:** 경기 시작 후 `0ms`부터 시작하는 **상대 시간(Relative Time)**.
- **유튜브 채팅:** `1730566871572`와 같은 **절대 시간(Unix Timestamp)**.
- **Flink의 제약:** Flink는 스트림 결합 시 가장 늦은 타임스탬프를 기준으로 워터마크(시간의 흐름)를 생성한다. 두 데이터의 시차가 너무 크면(수십 년), 과거 데이터는 '이미 지나간 데이터'로 간주되어 윈도우 조인에서 모두 유실(Drop)되는 현상이 발생함.

---

이 문제를 Flink 내부에서 해결하기 위해 다음과 같은 단계적 노력을 기울였음:

- **1차 시도 (Flink SQL 보정):** `CASE WHEN`문을 사용하여 경기별로 다른 오프셋(예: +55초)을 `timestamp`에 직접 더해주는 `adjusted_time` 로직을 Flink SQL 내부에 구현함.
- **발생한 문제 (Watermark Loss):** Flink SQL의 뷰(VIEW) 안에서 시간을 재계산하자, 해당 컬럼이 가지고 있던 '시간 속성(Time Attribute)'이 사라지고 단순한 `TIMESTAMP(3)` 타입으로 변해버림. 이로 인해 `Window aggregate can only be defined over a time attribute column` 에러가 발생하며 윈도우 연산이 불가능해짐.
- **2차 시도 (데이터 타입 충돌):** `victim_id`와 같은 필드가 숫자와 문자열이 혼재되어 파싱 에러가 나거나, 조인 키가 일치하지 않아 점수가 0점으로 집계되는 문제를 해결하기 위해 SQL 단계에서 `CAST` 연산을 도입함.

## 결정

Flink 엔진의 연산 부하를 줄이고 워터마크 유실 문제를 근본적으로 해결하기 위해 **'생산자(Producer) 단계의 시간 주입'** 전략으로 선회함.

1. **프로듀서 타임스탬프 덮어쓰기:** 파이썬 봇(game_bot, chat_bot)이 Kinesis로 데이터를 쏘는 찰나의 시스템 시간(`time.time()`)을 `timestamp` 컬럼에 주입하여 송출함.
2. **워터마크 재생성:** Flink에서는 주입된 `BIGINT` 타임스탬프를 초 단위로 변환 후, `WATERMARK` 구문을 통해 다시 시간 속성을 부여함.
3. **스키마 정규화:** Flink SQL에서 발생할 수 있는 파싱 에러를 방지하기 위해, 데이터를 쏘기 전 파이썬 단계에서 타입을 `STRING`으로 강제 통일함.

## 이유

- **성과:** Flink 내부의 복잡한 시간 보정 로직을 제거하여 파이프라인의 안정성을 확보하고, 1초 미만의 초저지연 조인을 실현함.
- **성과:** 과거 데이터를 활용해 실제 라이브 방송과 100% 동일한 환경에서 시스템 부하 테스트를 수행할 수 있게 됨.

## 트레이드오프

- **트레이드오프:** 리플레이 시뮬레이션을 위해 원본 발생 시간이 아닌 '데이터 처리 시점'을 이벤트 시간으로 사용함. (원본 시간은 `time_text` 필드에 보존하여 분석 가치 유지)

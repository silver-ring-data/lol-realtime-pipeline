## 배경

과거 인게임 이벤트와 시뮬레이션되는 채팅을 실시간으로 결합해야 하는데, 데이터마다 시간 기준이 달랐다. 인게임 데이터는 경기 시작 후 `0ms` 부터의 상대 시간, 유튜브 채팅은 Unix Timestamp 절대 시간이다. Flink 는 가장 늦은 타임스탬프 기준으로 워터마크를 생성하므로, 두 데이터의 시차가 크면 과거 데이터가 '이미 지나간 데이터'로 간주되어 윈도우 조인에서 모두 유실된다.

Flink 내부에서 해결하려는 시도가 있었다. 1차로 Flink SQL `CASE WHEN` 으로 경기별 오프셋(예: +55초)을 더한 `adjusted_time` 을 만들었으나, VIEW 안에서 시간을 재계산하자 시간 속성(Time Attribute)이 사라져 `Window aggregate can only be defined over a time attribute column` 에러가 발생했다. 2차로 `victim_id` 처럼 숫자·문자열이 혼재된 필드의 파싱 에러와 조인 키 불일치(점수 0점)를 `CAST` 로 해결하려 했다.

## 선택지

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. Producer 단계에서 전송 시각을 타임스탬프로 주입 | Flink 시간 보정 로직 제거, 워터마크 보존, 라이브와 동일한 환경 | 원본 발생 시간이 아닌 처리 시점을 이벤트 시간으로 사용 |
| B. Flink SQL 내 오프셋 보정 | Producer 수정 불필요 | 시간 속성 유실로 윈도우 연산 불가 |

## 결정

**A 를 채택한다.**

1. 파이썬 봇(game_bot, chat_bot)이 Kinesis 로 전송하는 순간의 시스템 시간(`time.time()`)을 `timestamp` 컬럼에 주입한다.
2. Flink 에서 `BIGINT` 타임스탬프를 초 단위로 변환한 뒤 `WATERMARK` 구문으로 시간 속성을 다시 부여한다.
3. 파싱 에러 방지를 위해 파이썬 단계에서 타입을 `STRING` 으로 강제 통일한다.

## 결과

- 좋아지는 것: 파이프라인 안정성 확보, 1초 미만 초저지연 조인, 라이브 방송과 100% 동일한 환경에서 부하 테스트 가능.
- 감수하는 것: 이벤트 시간이 원본 발생 시간이 아니다. 원본 시간은 `time_text` 필드에 보존하여 분석 가치를 유지한다.
- 다시 볼 조건: 실제 라이브 소스로 전환하여 원본 이벤트 시간을 그대로 쓸 수 있을 때.

# 0042. 실시간 시뮬레이션에 듀얼 타임(Base Time & Real Time) 동기화 전략을 적용한다

|---|---|

| 관련 | 0005, 0036, 0050 |

## 배경

과거 롤드컵 결승의 인게임 지표와 채팅을 Flink 윈도우 조인으로 결합하기 위해, 과거 데이터를 '지금 라이브로 방송되는 것처럼' Kinesis 로 전송하는 Producer 봇을 구축했다. 여기서 시간의 딜레마가 발생했다. 단순 현재 시간(`time.time()`)만 쓰면 게임 봇과 채팅 봇의 실행 타이밍(네트워크 지연, 컨테이너 기동 시간)이 미세하게 달라 싱크가 어긋나고, 과거 고정 시간을 쓰면 Flink 가 Late Data 로 간주해 워터마크가 꼬이고 데이터를 드롭한다.

## 선택지

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. Airflow Base Time + Producer Real Time 투트랙 | 봇 간 완벽한 싱크, 워터마크 안정, 제어 로직을 Airflow 로 분리 | 봇이 시작 시각을 인자로 받아야 함 |
| B. 각 봇의 현재 시간만 사용 | 단순 | 봇 간 싱크 어긋남 |
| C. 과거 고정 시간 사용 | 원본 시간 보존 | Late Data 로 드롭 |

## 결정

**A 를 채택한다.**

1. Base Time 주입: Airflow DAG 실행 시각(`{{ ts }}`)을 `sys.argv` 로 게임 봇과 채팅 봇에 동시에 주입하고, 모든 봇은 이를 시뮬레이션의 '0초'로 삼는다.
2. Smart Sleep: 봇 내부에서 `목표 시간 = Base Time + 설정된 지연(예: 55초)` 을 계산하여 목표 시간까지 스스로 대기 시간을 보정한다.
3. Real Time 타임스탬프: Kinesis 로 전송하는 찰나에 JSON 의 `timestamp` 에 실제 현재 시간을 덮어쓴다.

## 결과

- 좋아지는 것: 4경기(55초 대기), 5경기(3182초 대기) 등 어떤 시나리오에서도 봇 간 오차 없는 동기화가 가능하고, Flink 가 스트림을 현재 발생하는 라이브 이벤트로 인식한다. "언제, 어떤 경기를 시작할 것인가"는 Airflow 가 담당한다.
- 감수하는 것: 봇 실행 인터페이스 변경.
- 다시 볼 조건: 실제 라이브 소스로 전환할 때.

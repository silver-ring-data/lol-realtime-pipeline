# 0042. 실시간 스트리밍 시뮬레이션을 위한 듀얼 타임(Base Time & Real Time) 동기화 전략

## 현상

- 본 프로젝트는 과거 롤드컵 결승전의 정형 데이터(인게임 지표)와 비정형 데이터(채팅)를 Flink의 윈도우 연산(Window Join)으로 실시간 결합하여 하이라이트를 추출함.
- 이를 위해 과거 데이터를 마치 **'지금 라이브로 방송되는 것처럼'** Kinesis로 전송하는 파이썬 봇(Producer)을 구축함.
- **발생한 문제 (시간의 딜레마):**
  1. **단순 현재 시간(`time.time()`) 사용 시:** 게임 봇과 채팅 봇이 실행되는 물리적인 타이밍(네트워크 지연, 컨테이너 기상 시간 등)이 미세하게 달라, 두 스트림의 싱크가 어긋나고 조인(Join) 정확도가 하락함.
  2. **과거 고정 시간(예: 1970년) 사용 시:** Flink가 해당 데이터를 '너무 늦게 도착한 과거 데이터(Late Data)'로 간주하여 워터마크(Watermark) 생성이 꼬이고 윈도우 연산에서 데이터를 통째로 드롭(Drop)해버림.

## 결정

**오케스트레이터(Airflow) 기반의 'Base Time'과 프로듀서(Python) 기반의 'Real Time'을 혼합 사용하는 투트랙 시간 동기화 전략**을 채택함.

1. **지휘자의 출발 총소리 (Base Time 주입):**
   - Airflow DAG가 실행되는 순간의 절대 시각(`{{ ts }}`)을 `sys.argv`를 통해 게임 봇과 채팅 봇에 동시에 주입함.
   - 모든 봇은 자신이 언제 켜졌는지와 무관하게, 이 Base Time을 전체 시뮬레이션의 '0초(기준점)'로 삼음.
2. **스마트 대기 로직 (Smart Sleep):**
   - 봇 내부에서 `목표 시간 = Base Time + 설정된 지연 시간(예: 55초)`을 계산하여, 목표 시간에 도달할 때까지 스스로 대기 시간을 보정함.
3. **데이터의 발도장 (Real Time 타임스탬프):**
   - 대기를 마치고 Kinesis로 데이터를 쏘는 찰나에, 데이터 JSON 내부의 `timestamp` 필드에 실제 현재 시간(`time.time()`)을 덮어씌움.

## 이유

- **완벽한 스트림 동기화 (Perfect Synchronization):** 각 봇이 독립적으로 실행되더라도 Airflow가 부여한 단일 기준점(Base Time)을 공유하므로, 4경기(55초 대기)와 5경기(3182초 대기) 등 어떠한 시나리오에서도 0.1초의 오차 없는 칼군무(Sync)가 가능해짐.
- **Flink 연산 최적화 (Watermark Stability):** 데이터 내부에 진짜 실시간 타임스탬프가 찍혀 들어가므로, Flink 엔진이 스트림을 '현재 발생하는 라이브 이벤트'로 정확히 인식하고 윈도우 조인 및 워터마크 처리를 지연 없이 완벽하게 수행함.
- **관심사의 분리 (Separation of Concerns):** 봇(Producer) 코드는 파라미터를 받아 실행하고 데이터를 전송하는 역할만 수행하며, "언제, 어떤 경기를 시작할 것인가"에 대한 제어 로직은 Airflow로 완전히 분리되어 유지보수성이 극대화됨.

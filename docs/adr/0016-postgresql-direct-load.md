## 배경

분석 결과의 영구 저장·대용량 분석을 위해 Firehose → S3 적재 경로는 이미 있다. 여기에 더해 실시간 대시보드용 PostgreSQL 적재 방식을 두고 두 가지 대안을 검토했다.

## 선택지

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 직접 적재: `Flink → PostgreSQL` (JDBC Sink) | 수초 이내 지연, S3 버퍼링 회피, 파이프라인 단순화 | Flink 잡 복잡도 증가(S3·DB 적재 로직 공존), DB 쓰기 부하 |
| B. S3 경유: `Flink → S3 → Batch/Lambda → PostgreSQL` | 단일 경로 | S3 버퍼링(최소 1분)으로 실시간 요건 미충족 |

## 결정

**A 를 채택한다.** 하이라이트 점수, 현재 킬 스코어 등 분석 완료 결과는 S3 를 거치지 않고 JDBC Sink Connector 로 바로 PostgreSQL 에 INSERT 한다. 원본과 모든 과거 분석 기록은 기존대로 S3 에 영구 저장하는 '듀얼 적재(Dual-loading)' 를 유지한다. S3 는 아카이빙·과거 분석용, PostgreSQL 은 API 서버의 실시간 서빙용으로 용도를 분리한다.

## 결과

- 좋아지는 것: 대시보드 그래프가 라이브 화면과 거의 동시에 변동하고, API 서버가 S3 대신 최적화된 DB 에서 조회하여 로딩이 빠르다.
- 감수하는 것: 스키마 변경 시 두 적재 로직 모두 영향을 받는다. 초당 수천 건 INSERT 에 대비해 DB 인스턴스 스케일링이 필요하다.
- 다시 볼 조건: DB 쓰기 부하가 한계에 도달할 때. (0029 에서 RDS 자체를 제거하며 폐기되었다.)

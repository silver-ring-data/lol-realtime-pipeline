## 현상

우리는 분석 결과의 **영구 저장 및 대용량 분석**을 위해 Amazon Data Firehose를 통해 S3로 데이터를 적재하는 경로를 이미 가지고 있다. 이에 따라, Postgres 적재 방식을 두고 두 가지 대안을 고민하게 되었다.

1. **S3 경유 적재 (Staged Load):** `Flink` → `S3` → `Batch Job/Lambda` → `PostgreSQL`
2. **직접 적재 (Direct Load):** `Flink` → `PostgreSQL` (JDBC Connector 사용)

## 결정

우리는 **'대안 2: 직접 적재 (Direct Load)'** 전략을 채택한다.

Flink에서 분석 완료된 알짜배기 결과 데이터(하이라이트 점수, 현재 킬 스코어 등)는 S3를 거치지 않고, Flink 내부의 **JDBC Sink Connector를 사용하여 곧바로 PostgreSQL로 `INSERT` 한다.**

단, 원본 데이터 및 모든 과거 분석 기록은 기존 설계대로 S3(데이터 레이크)에 영구 저장하는 **'듀얼 적재(Dual-loading)'** 아키텍처를 유지한다.

## 이유

- **초저지연(Ultra-low Latency) 달성:** 우리 프로젝트의 가장 중요한 가치는 유튜브 하이라이트보다 빠르게 실시간 기세를 시각화하는 것이다. S3를 경유하는 방식은 S3의 버퍼링 시간(최소 1분 이상)으로 인해 '실시간' 대시보드의 요건을 충족할 수 없다. Flink에서 직접 Postgres로 쏠 경우 지연 시간을 수초 이내로 단축할 수 있다.
- **데이터의 용도 분리 (Separation of Concerns):** S3는 대용량 아카이빙 및 과거 데이터 분석용이고, PostgreSQL은 API 서버가 대시보드 그래프를 그리기 위한 실시간 서비스용이다. 용도에 맞게 저장소를 분리하여 최적화된 성능을 얻기 위함이다.
- **구조적 간결함 (Simplification):** 실시간 데이터 흐름에서 S3를 거쳐 Lambda나 배치 잡을 트리거 하는 복잡한 로직을 제거하여 파이프라인의 관리 포인트를 줄인다.

## 트레이드오프

### 긍정적인 측면 (Pros)

- **실시간 성능 최적화:** 대시보드 그래프가 거의 라이브 화면과 동시에 변동하게 만들어 최고의 사용자 경험을 제공할 수 있다.
- **API 서버 성능 보장:** API 서버가 S3를 뒤질 필요 없이 최적화된 PostgreSQL에서 데이터를 가져오므로 대시보드 로딩 속도가 매우 빠르다.

### 부정적인 측면 (Cons) / 고려 사항

- **Flink 잡 복잡도 증가:** Flink 잡 내부에 S3 적재 로직과 PostgreSQL 적재 로직이 모두 들어가야 하므로, 잡의 스키마 변경 시 두 곳 모두 영향을 받게 된다.
- **PostgreSQL 쓰기 성능 dependency:** Flink가 초당 수천 건의 INSERT를 날릴 경우 PostgreSQL에 부하가 갈 수 있으므로, DB 인스턴스 사량을 적절히 스케일링해야 한다.

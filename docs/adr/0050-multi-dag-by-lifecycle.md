## 배경

초기에는 인프라 초기화(DDL 생성, S3 정리), 실시간 수집 봇 실행, 경기 종료 후 배치 분석(Athena/Glue)이 하나의 거대한 DAG 에 묶여 있었다. 이 작업들은 실행 주기와 성격이 완전히 다르다(인프라 세팅은 최초 1회, 봇은 경기 내내, 배치는 종료 신호 이후). 단일 DAG 에서는 한 작업의 지연·에러가 무관한 실시간 수집까지 막는 병목과 단일 장애점(SPOF) 문제가 생긴다.

## 선택지

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 인프라 세팅 / 실시간 수집 / 배치 분석 3개 DAG 로 분리 | 장애 격리, 유지보수성, 생명주기별 센서·트리거 설정 | DAG 간 연계 관리 |
| B. 단일 DAG 유지 | 한눈에 보임 | SPOF, 병목 |

## 결정

**A 를 채택한다.**

- DAG 1 인프라 세팅: 경기 시작 전 S3 경로 청소 및 Athena DDL 사전 생성. 파이프라인 가동 전 1회성 실행.
- DAG 2 실시간 수집: 게임 봇과 채팅 봇을 병렬 가동하여 Kinesis 로 전송. 경기 시작과 동시에 트리거되어 끝날 때까지 지속 실행.
- DAG 3 배치 분석·리포팅: 넥서스 파괴 시 생성되는 `finished.txt` 를 `S3KeySensor` 로 감지하여 Glue ETL 과 Athena 최종 골드 리포트 생성. 실시간 스트리밍과 비동기로, 경기 종료 조건이 만족될 때만 실행.

## 결과

- 좋아지는 것: 배치 분석 오류가 나도 실시간 수집은 계속 Kinesis 로 데이터를 보내 유실을 방지하고, 목적에 맞는 DAG 파일만 수정하면 되며, 진정한 이벤트 기반 파이프라인이 된다.
- 감수하는 것: DAG 간 연계 관리.
- 다시 볼 조건: DAG 수가 늘어 공통 모듈 추출이 필요할 때.

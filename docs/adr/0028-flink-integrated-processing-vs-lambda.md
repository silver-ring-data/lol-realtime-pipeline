# 0028. (Lambda 관련)실시간 데이터 정제 및 집계 아키텍처 통합 결정

| 상태 | 날짜 |
|---|---|
| 폐기 | 2026-04-28 |

## 현상

- 현재 파이프라인은 `Kinesis Data Streams`를 통해 들어오는 대량의 비정형 채팅 데이터와 정형 게임 데이터를 처리하고 있음.
- 설계 초기 단계에서는 Flink의 부하를 줄이기 위해 AWS Lambda를 활용하여 앞단에서 데이터를 미리 정제(Flattening, Filtering)하는 방식을 검토함.
- 하지만 시스템의 실시간성 유지, 인프라 관리 복잡도, 그리고 제한된 예산(월 6만 원) 내에서의 효율적인 운영 방안에 대한 재검토가 필요해짐.

## 결정

- **Option A: Lambda 기반 사전 정제 루트**
  - 구조: `Kinesis -> Lambda (정제) -> Kinesis -> Flink (집계)`
  - 특징: Flink의 연산 부하를 분산할 수 있으나, 서비스 간 네트워크 홉(Hop)이 추가되어 미세한 지연 시간(Latency)이 발생하고 Lambda 호출 비용이 추가됨.
- **Option B: Flink 통합 처리 루트 (현재 채택)**
  - 구조: `Kinesis -> Flink (정제 + 집계 통합)`
  - 특징: 단일 엔진에서 모든 로직을 처리하여 지연 시간을 최소화하고 아키텍처를 단순화함.

최종적으로 [Option B: Flink 통합 처리] 방식을 유지하기로 결정함.

## 이유

1. **비용 효율성 극대화:** Amazon Managed Service for Apache Flink(KDA)는 최소 1 KPU의 고정 비용이 발생함. 현재 우리 프로젝트의 트래픽 규모(초당 수백 건)는 1 KPU 내에서 정제와 집계를 모두 처리하기에 충분하며, Lambda를 추가할 경우 오히려 불필요한 추가 과금이 발생함.
2. **초저지연(Low Latency) 달성:** 하이라이트 탐지는 '속도'가 생명임. 중간에 Lambda와 추가 스트림을 거치지 않음으로써 네트워크 지연 요소를 제거하고 데이터 흐름을 단순화함.
3. **운영 편의성:** 여러 서비스를 연동하는 것보다 Flink SQL 내에서 `JSON_VALUE` 및 필터링 로직을 통합 관리하는 것이 유지보수 측면에서 더 유리함.
4. **확장성 확보:** 추후 트래픽이 기하급수적으로 늘어나 KPU 사용량이 임계치에 도달할 경우, 그때 Lambda를 분리하는 'Scale-out' 전략을 취하는 것이 비용 최적화 관점에서 더 타당함.

## 트레이드오프

- **긍정적 효과:** 월 예산 내에서 안정적인 운영 가능, 아키텍처의 단순함으로 인한 트래블슈팅 용이성.
- **부정적 효과:** Flink 로직(SQL)이 상대적으로 길어질 수 있으나, 뷰(VIEW)와 모듈화된 쿼리 작성을 통해 극복 가능함.

# 0043. 사용자 경험 극대화 및 비용 최적화를 위한 완전 서버리스(Serverless) 서빙 아키텍처 채택

> 원본: https://app.notion.com/p/3561198df8d980c8be14f02772ecdd4d

| 상태 | 날짜 |
|---|---|
| 채택 | 2026-05-04 |

## 현상

- **트래픽 변동성:** '실시간 롤 응원석' 서비스는 경기 진행 여부나 주요 교전(하이라이트) 발생 시점에 따라 트래픽이 급격히 치솟는 '스파이크(Spike)' 현상이 빈번하게 발생함.
- **비용 효율성:** 고정된 사양의 EC2를 24시간 운영할 경우, 경기가 없는 시간대에도 비용이 발생하여 한정된 예산(6만 원) 관리에 어려움이 있음.
- **운영 부담:** 서버 가용성을 유지하기 위한 OS 업데이트, 패치, 스케일링 설정 등을 직접 관리하는 것은 소규모 팀에게 과도한 리소스 소모를 야기함.

## 결정

전통적인 서버 기반(EC2) 서빙 구조를 완전히 걷어내고, AWS의 완전 관리형 서버리스 서비스를 조합한 아키텍처를 채택함.

- **프론트엔드 서빙:** **Amazon S3 + CloudFront**
  - 빌드된 정적 리소스(HTML/JS/CSS)를 S3 버킷에 호스팅하고, CDN인 CloudFront를 통해 전 세계 유저에게 저지연(Low Latency)으로 배달함.
- **백엔드 API:** **Amazon API Gateway + AWS Lambda**
  - API 서버를 상시 가동하지 않고, 요청이 들어올 때만 람다 함수가 깨어나 OpenSearch 및 RDS에서 데이터를 조회하여 응답함.
- **보안 및 최적화:** CloudFront를 통해 S3 직접 접근을 차단(OAI/OAC)하고, API Gateway에서 Throttling 설정을 통해 비정상적인 요청을 방어함.

## 이유

1. **가성비 극대화 (Pay-as-you-go):** 사용자가 접속할 때만 비용이 발생하는 구조로, 경기가 없는 대부분의 시간 동안 인프라 비용을 0원에 가깝게 유지할 수 있음.
2. **무한 확장성 (Serverless Scaling):** 롤드컵 결승전과 같이 수만 명의 팬들이 동시에 하이라이트 지표를 요청해도, 별도의 서버 증설 작업 없이 AWS가 자동으로 람다 인스턴스를 확장하여 대응함.
3. **데이터 엔지니어링 집중:** 서버 인프라 관리(Maintenance) 시간을 절약하여 Flink 윈도우 조인 및 데이터 정제 로직 고도화에 더 많은 시간을 할애할 수 있음.

## 트레이드오프

- **긍정적 효과:**
  - 웹 서비스 응답 속도 향상 (CloudFront의 엣지 캐싱 활용).
  - 고정 비용 소멸로 인한 프로젝트 유지 기간 연장.
  - "인프라 운영 효율화"라는 기술적 어필 포인트 확보.
- **부정적 효과:**
  - 람다의 **Cold Start** 이슈가 발생할 수 있으나, 가벼운 Python 코드 위주이므로 사용자 경험을 해치지 않는 수준(수백 ms 이내)으로 제어 가능함.

## 배경

실시간 하이라이트 탐지는 초저지연 처리가 핵심이다. 원본(Bronze) 스트림에는 시스템 메시지(Nightbot), 하이라이트와 무관한 지속 성장 지표(CS 등), 복잡한 파싱이 필요한 배열 데이터가 포함되어 있다. 이를 그대로 Flink 로 넘겨 윈도우 조인하면 메모리를 불필요하게 차지하고 병목이 된다.

## 선택지

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 노이즈 필터링 + 컬럼 드롭 + 배열→정수 변환 | 연산 속도 극대화, 페이로드 축소로 비용 절감, 데이터 품질 향상 | 변환 로직 추가 |
| B. 원본 그대로 Flink 연산 | 변환 불필요 | 메모리 낭비, 병목 |

## 결정

**A 를 채택한다.**

- A. 채팅 정제: Flink SQL `WHERE` 절로 `nickname = '@nightbot'` 및 `[warning]` 패턴을 필터링하여 순수 유저 채팅만 실버 스트림에 적재한다.
- B. 인게임 데이터 다이어트: `minions_killed` 필드를 드롭하고 격차 계산용 `total_gold` 만 유지한다.
- C. 타입 변환: `assisting_participant_ids`(배열)를 Producer 단에서 배열 길이인 `assist_count`(정수)로 변환하여 전송한다.

## 결과

- 좋아지는 것: Flink 는 `kill_score + (assist_count * 가중치)` 형태의 단순 사칙연산만 수행하고, Kinesis·Firehose·S3 비용이 줄며, 봇 채팅이 제거된 데이터만 Gold 로 전달된다.
- 감수하는 것: 변환 로직 유지.
- 다시 볼 조건: 전처리 위치(Producer vs Flink)를 재검토할 때 (0026 에서 C 항목의 위치가 Flink 로 변경되었다).

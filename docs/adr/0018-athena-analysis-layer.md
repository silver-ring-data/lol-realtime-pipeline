# 0018. 비용 효율성 및 안정성을 고려한 Amazon Athena 분석 레이어 채택

> 원본: https://app.notion.com/p/3491198df8d980349d70c60569d93eaf

| 상태 | 날짜 |
|---|---|
| 채택 | 2026-04-21 |

## 현상

- 우리 프로젝트의 핵심은 '실시간' 하이라이트 탐지이기 때문에 메인 엔진은 flink로 채택하였습니다.
- 그래서 실시간성으로 사용하기는 조금 어려운 athena를 프로젝트에서 제외할까 고민을 하였습니다.
- 그러나 실시간 처리 엔진인 Apache Flink는 데이터를 영구 저장하지 않으며, 조인을 위해 메모리에 데이터를 들고 있는 비용(State Cost)이 발생합니다.
- 모든 분석 요구사항을 실시간 엔진에서만 처리하거나 상시 가동되는 데이터베이스(RDS 등)에 모든 데이터를 넣는 방식은 불필요한 인프라 비용을 초래할 수 있습니다.

## 결정

- 실시간 서빙용 DB와는 별개로, **가성비가 뛰어난 S3(저장) + Athena(쿼리)** 조합을 배치/분석 레이어로 유지합니다.

## 이유

- **상시 인프라 비용(Fixed Cost)의 최소화:**
  - **PostgreSQL/RDS:** 데이터가 늘어날수록 저장 공간 비용이 비싸지고, 사용하지 않는 시간에도 인스턴스 사양에 따른 고정 비용이 발생합니다.
  - **Athena:** 서버가 없는(Serverless) 구조로 기본료가 **0원**입니다. 오직 쿼리를 던져서 스캔한 데이터 양(1TB당 $5)에 대해서만 과금되므로, 가끔 발생하는 사후 분석용으로 최적의 가성비를 가집니다.
- **Flink 메모리 부하 분산:**
  - Flink가 모든 과거 데이터를 기억하려면 대용량 메모리가 필요하고 이는 곧 비용 상승으로 이어집니다.
  - **전략:** Flink는 '실시간 조인'을 위한 최소한의 데이터(최근 3~5분)만 메모리에 들고 있게 하여 인프라 사양을 낮추고, 4분 이전의 과거 데이터 분석은 Athena에게 넘겨 **실시간 엔진의 비용을 다이어트** 시킵니다.
- **저장 비용의 극대화 (S3 활용):**
  - 모든 채팅 로그와 게임 이벤트를 DB에 저장하는 것보다, 세상에서 가장 저렴한 저장소인 S3에 원본(Raw) 상태로 두고 필요할 때만 Athena로 쿼리하는 것이 데이터 보존 측면에서 수십 배 경제적입니다.
- **운영 안정성 및 재현성 확보:**
  - 실시간 로직에 오류가 발견되어 재계산이 필요할 때, 비싼 DB를 풀 스캔하는 대신 Athena를 활용해 저렴하고 빠르게 로직 검증을 수행할 수 있습니다.

[기대효과]

- **비용 절감:** 상시 가동되는 분석용 서버 없이도 대규모 로그 분석 환경을 구축하여 전체 프로젝트 유지 비용을 80% 이상 절감할 수 있습니다.
- **전문성 증명:** "단순히 기능만 구현한 것이 아니라, 데이터의 특성에 따라 '실시간은 Flink', '비정형 대규모 분석은 Athena'로 나누어 **인프라 비용을 최적화(Cost Optimization)** 하는 설계를 지향했습니다"라고 당당하게 어필할 수 있습니다.

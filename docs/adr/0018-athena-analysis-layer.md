## 배경

핵심이 '실시간' 탐지이므로 메인 엔진은 Flink 로 정했고, 실시간성이 떨어지는 Athena 를 제외할지 고민했다. 그러나 Flink 는 데이터를 영구 저장하지 않고 조인용 상태를 메모리에 들고 있는 비용(State Cost)이 발생한다. 모든 분석을 실시간 엔진에서 처리하거나 상시 가동 DB(RDS)에 모든 데이터를 넣는 방식은 불필요한 인프라 비용을 초래한다.

## 선택지

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. S3(저장) + Athena(쿼리)를 배치/분석 레이어로 유지 | 기본료 0원(스캔량 과금), Flink 메모리 부하 분산, 저렴한 원본 보존, 재계산 용이 | 실시간 조회에는 부적합 |
| B. 모든 분석을 Flink 또는 RDS 에서 처리 | 구성 요소 감소 | 고정 비용, 메모리 비용 상승 |

## 결정

**A 를 채택한다.** 실시간 서빙 DB 와 별개로 S3 + Athena 조합을 배치/분석 레이어로 유지한다. Flink 는 실시간 조인에 필요한 최소 데이터(최근 3~5분)만 메모리에 들고, 그 이전 과거 데이터 분석은 Athena 에 넘긴다.

## 결과

- 좋아지는 것: 상시 분석 서버 없이 대규모 로그 분석 환경을 구축하여 유지 비용을 크게 절감하고, 실시간 로직 오류 시 DB 풀 스캔 대신 Athena 로 저렴하게 재검증한다.
- 감수하는 것: 두 개의 분석 경로를 관리한다.
- 다시 볼 조건: Athena 스캔 비용이 상시 DB 비용을 넘어설 만큼 쿼리가 잦아질 때.

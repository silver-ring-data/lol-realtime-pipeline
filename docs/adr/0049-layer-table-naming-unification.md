# 0049. 레이어 및 테이블 식별을 위한 Naming Convention 통일 전략

## 현상

- 람다 아키텍처(Lambda Architecture)를 도입하면서, 동일한 데이터를 처리하더라도 실시간 스트리밍(Speed) 레이어와 배치(Batch) 레이어에서 각각 별도의 테이블을 생성해야 함.
- 이로 인해 두 레이어의 테이블 이름이 혼재될 경우, 쿼리 작성 및 분석 시 치명적인 조인(Join) 오류나 시점(Time-sync) 불일치 문제가 발생할 수 있음.
- 또한, 기존 PyFlink 환경에서는 뷰(View)와 테이블(Table)을 구분하기 위해 이미 `_tbl` 접미사를 사용하고 있었으나, Athena(배치 레이어) 쪽 명명 규칙은 이를 일관되게 따르지 않고 있었음.

## 결정

모든 데이터베이스 및 카탈로그의 테이블 이름에 대해 다음과 같은 명시적인 접두사(Prefix)와 접미사(Suffix)를 강제하는 **Naming Convention**을 채택함.

- **접두사 (Prefix): 데이터의 호흡(주기) 구분**
  - 배치 처리용 테이블: `btch_` (예: `btch_slv_game`)
  - 실시간 스트리밍용 테이블: `strm_` (예: `strm_slv_chat`)
- **접미사 (Suffix): 객체 타입 명시**
  - 물리적으로 데이터가 저장되는 모든 테이블에는 `_tbl`을 필수로 붙임. (예: `btch_slv_game_tbl`)

## 이유

- **"시간차 대참사" 원천 차단:** 배치(어제 데이터)와 스트리밍(1초 전 데이터)을 무심코 조인하는 실수를 이름 레벨에서 직관적으로 방지함.
- **엔진별 쿼리 전략의 시각화:** 이름표만 보고도 "이건 Flink(스트리밍) 쿼리용이네", "이건 Athena(배치) 쿼리용이네"를 판단하여 문법 스위칭을 용이하게 함.
- **프로젝트 일관성(Consistency):** PyFlink 영역에서 이미 자연스럽게 사용 중이던 `_tbl` 접미사 규칙을 프로젝트 전체로 확장하여, 아키텍처의 설계 철학이 코드 레벨까지 통일되게 스며들도록 함.

## 트레이드오프

- **장점:** 아키텍처 다이어그램과 실제 코드(DB 스키마)가 완벽하게 일치하여, 시스템의 가독성과 유지보수성이 극대화됨. 협업 시 팀원들의 커뮤니케이션 미스를 줄임.
- **단점:** 테이블 이름이 다소 길어질 수 있음. (그러나 명확성이 주는 이득이 훨씬 큼)

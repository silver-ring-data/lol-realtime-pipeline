## 배경

람다 아키텍처(Lambda Architecture)를 도입하면서 동일 데이터라도 실시간 스트리밍(Speed) 레이어와 배치(Batch) 레이어에서 각각 별도 테이블을 생성해야 한다. 두 레이어의 테이블 이름이 혼재되면 조인 오류나 시점(Time-sync) 불일치가 발생할 수 있다. PyFlink 에서는 View 와 Table 을 구분하기 위해 이미 `_tbl` 접미사를 쓰고 있었으나, Athena 쪽 명명은 이를 따르지 않았다.

## 선택지

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 접두사(`btch_`/`strm_`) + 접미사(`_tbl`) 강제 | 배치·스트리밍 혼동 방지, 엔진별 쿼리 전략 시각화, 프로젝트 일관성 | 테이블 이름이 길어짐 |
| B. 자유 명명 | 짧은 이름 | 시간차 조인 실수 위험 |

## 결정

**A 를 채택한다.**

- 접두사(데이터 주기): 배치 `btch_` (예: `btch_slv_game`), 실시간 스트리밍 `strm_` (예: `strm_slv_chat`)
- 접미사(객체 타입): 물리적으로 데이터가 저장되는 모든 테이블에 `_tbl` 필수 (예: `btch_slv_game_tbl`)

## 결과

- 좋아지는 것: 배치(어제 데이터)와 스트리밍(1초 전 데이터)을 무심코 조인하는 실수를 이름 레벨에서 방지하고, 아키텍처 다이어그램과 실제 DB 스키마가 일치한다.
- 감수하는 것: 긴 테이블 이름. 명확성의 이득이 더 크다.
- 다시 볼 조건: 새 레이어(예: 서빙 전용)가 추가되어 접두사 확장이 필요할 때.

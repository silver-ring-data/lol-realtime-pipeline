## 배경

실시간 하이라이트 탐지 시스템의 신뢰성을 증명해야 하지만, 실제 API 데이터는 시차(3분 지연)와 불확실성(데이터 발생 여부)이 있어 초기 로직 개발·디버깅이 어렵다. 안정적인 로직 구축과 실무 수준 배포를 위해 단계별 접근이 필요하다.

## 선택지

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. Phase 1(정적 검증) → Phase 2(실전 API·클러스터 배포) 분리 | 정확도를 먼저 증명한 뒤 확장하는 서사, 배포 가능한 구조 확보 | 두 단계의 개발 환경 유지 |
| B. 처음부터 실전 API 연동 | 단계 축소 | 시차·불확실성으로 디버깅 곤란 |

## 결정

**A 를 채택한다.**

| 비교 항목 | Phase 1 | Phase 2 |
|---|---|---|
| 주요 대상 | 2024 월즈 결승 (T1 vs BLG) | 프로 선수 실시간 솔랭 및 방송 채팅 |
| 데이터 소스 | GOL.GG(게임), 유튜브 VOD(채팅) | Riot Spectator API, 실시간 스크래퍼 |
| 개발 환경 | Kinesis Studio Notebook | Apache Flink Application (JAR 배포) |
| 핵심 목표 | 하이라이트 판별 로직 정확도 검증 | 시스템 가용성 및 시차(Skew) 해결 능력 증명 |
| 검증 포인트 | 한타 발생 시 점수가 폭등하는가 | 3분 지연 데이터를 실시간 채팅과 맞추는가 |

- Phase 1: 정답이 알려진 과거 명경기 JSON 을 Replay 하여 Studio Notebook 에서 윈도우 조인·스코어링 알고리즘을 튜닝한다.
- Phase 2: Flink 코드를 JAR 로 패키징하여 클러스터에 배포하고, Riot API 3분 지연을 `Watermark`, `Allowed Lateness`, `ProcessFunction` 상태 관리로 처리하며, Discord/Telegram 실시간 알림을 연동한다.

## 결과

- 좋아지는 것: 논리적 빌드업으로 신뢰도 상승, '비정기적 실시간 스트림 조인'과 '시간 지연 제어' 경험 확보, 노트북 기반 휘발성 코드가 아닌 배포 가능한 구조.
- 감수하는 것: Phase 2 는 별도 리소스가 필요하다.
- 다시 볼 조건: Phase 1 완료 후 Phase 2 착수 시점을 정할 때.

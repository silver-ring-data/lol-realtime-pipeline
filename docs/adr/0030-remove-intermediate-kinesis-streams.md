# 0030. 파이프라인 효율화: 중간 단계(Silver,Gold) Kinesis 스트림 제거 및 Flink 인메모리 처리 전환

## 현상

- 초기 설계에서는 메달리온 아키텍처의 각 단계(Bronze → Silver → Gold)마다 물리적인 데이터 통로인 **Kinesis Data Streams**를 배치하려고 함.
- 이 방식은 단계별로 데이터를 영구 저장할 수 있어 안정적이지만, 다음과 같은 치명적인 단점이 존재함:
  1. **비용 폭발:** Kinesis는 샤드(Shard) 수에 따라 시간당 비용이 발생하므로, 스트림 개수가 늘어날수록 우리 프로젝트 예산(6만 원)을 초과할 위험이 큼.
  2. **지연 시간(Latency) 증가:** 데이터를 매번 스트림에 쓰고(Write) 다시 읽는(Read) 과정에서 미세한 네트워크 오버헤드가 발생하여 초저지연 성능을 저해함.

## 결정

- **Silver 단계 전용 Kinesis 스트림을 아예 생성하지 않기로 결정함.**
- 대신, Flink 엔진 내부에서 **인메모리(In-memory) 임시 테이블**을 활용하여 실시간 정제 및 조인 연산을 한 번에 수행한다.
- 연산이 끝난 최종 결과물(Gold)만 최종 목적지(OpenSearch)로 filesink를 이용해 바로 전송한다.

## 이유

- **가성비의 극대화 (Cost Efficiency):** 불필요한 Kinesis 스트림 1~2개를 제거함으로써 월 수십 달러의 비용을 절감하고, 한정된 자원을 더 중요한 연산(Flink KPU 등)에 집중할 수 있음.
- **초저지연 성능 확보 (Performance):** 데이터를 외부 스트림으로 내보내지 않고 Flink 내부 메모리에서 직접 다음 연산으로 넘기기 때문에 지연 시간을 '밀리초(ms)' 단위로 단축함.
- **아키텍처의 단순화 (Simplicity):** 인프라 관리 포인트가 줄어들어 전체 시스템의 유지보수성이 향상됨.

## 트레이드오프

- Flink SQL 로직이 `INSERT INTO Silver_Stream` -> `SELECT FROM Silver_Stream` 구조에서, 하나의 거대한 뷰(View) 또는 연속적인 연산(Chaining) 구조로 변경됨.
- 만약 Flink Job이 멈출 경우 Silver 단계의 데이터를 스트림에서 다시 복구할 수 없다는 위험이 있지만, 이는 **Checkpointing 기능을 활성화**하여 Flink 내부 상태를 S3에 저장함으로써 보완함.

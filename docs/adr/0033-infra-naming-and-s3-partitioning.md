# 0033. 인프라 네이밍 컨벤션 및 S3 데이터 파티셔닝 전략 수립

> 원본: https://app.notion.com/p/3521198df8d980a48deefa0ef6c2c73b

| 상태 | 날짜 |
|---|---|
| 채택 | 2026-04-30 |

## 현상

- **리소스 식별 문제:** 학원 공용 AWS 계정을 사용함에 따라, 다른 사용자들과 리소스가 섞이지 않도록 명확한 소유권 식별이 필요함.
- **쿼리 성능 및 비용:** S3에 저장되는 데이터(채팅, 게임 로그)가 누적될수록 Athena 등 분석 도구의 데이터 스캔량이 늘어나 비용이 기하급수적으로 증가할 위험이 있음.
- **관리 복잡도:** 메달리온 아키텍처(Bronze/Silver/Gold)에 따라 데이터의 정제 상태가 다르므로, 이를 직관적으로 파악할 수 있는 저장 구조가 필요함.

## 결정

### 2.1 AWS 리소스 명명 규칙 (Naming Convention)

모든 AWS 리소스(Kinesis, RDS, S3 등)는 아래 포맷을 필수적으로 준수한다.

> **`{user_id}-{project}-{env}-{region_abbr}-{service}-{tier}-{data}`**

- 예: `{user_id}-lol-dev-an2-kds-brz-chat`

### 2.2 S3 데이터 레이크 폴더 구조 (Partitioning)

조회 빈도와 데이터 성격을 고려하여 **`Tier > Data Type > Match ID > Date`** 순서로 계층을 구성한다.

- **Hierarchy:** `s3://bucket/tier/data_type/match_id/yyyy-mm-dd/`
- **적용 예시:** `s3://{bucket}/bronze/chat/match_t1_blg_01/2024-11-02/`

## 이유

1. **거버넌스(Governance) 확보:** `user_id`를 최상위 식별자로 사용하여 공용 계정 내 리소스 충돌을 원천 차단함.
2. **비용 최적화 (Athena Partitioning):** `Match ID`와 `Date`를 하위 파티션으로 두어, 특정 경기 분석 시 불필요한 데이터를 읽지 않도록 설계(Data Skipping). 이는 Athena 쿼리 비용을 **80% 이상 절감**할 수 있는 핵심 전략임.
3. **메달리온 아키텍처 준수:** `Tier(Bronze/Silver/Gold)`를 최상위 폴더로 두어 데이터의 신뢰도와 가공 상태를 엔지니어가 즉각적으로 파악할 수 있게 함.
4. **관심사 분리:** 설정 파일 관리 시, 구조적 정보(`config.yaml`)와 보안 정보(`.env`)를 분리하여 보안성과 협업 효율을 동시에 챙김.

## 트레이드오프

- **긍정적 효과:**
  - 팀원 및 면접관에게 체계적인 인프라 관리 역량을 증명할 수 있음.
  - 대규모 데이터셋 추가 시에도 코드 수정 없이 YAML 설정 변경만으로 유연하게 대응 가능함.
  - 데이터 분석 시 쿼리 속도가 향상되고 AWS 비용 발생을 최소화함.
- **부정적 효과:**
  - 데이터 저장 시 Prefix(경로)가 다소 길어질 수 있으나, 자동화 스크립트(boto3 등)로 충분히 해결 가능한 수준임.

# 0033. 인프라 네이밍 컨벤션과 S3 데이터 파티셔닝 전략을 수립한다

| | |
|---|---|
| 상태 | **채택** |

| 관련 | 0012, 0023, 0035 |

## 배경

교육 기관 공용 AWS 계정을 사용하므로 다른 사용자와 리소스가 섞이지 않도록 소유권 식별이 필요하다. S3 에 채팅·게임 로그가 누적될수록 Athena 스캔량이 늘어 비용이 증가할 위험이 있다. 메달리온 아키텍처의 정제 상태를 직관적으로 파악할 수 있는 저장 구조도 필요하다.

## 선택지

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. `{user_id}` 접두사 포함 명명 규칙 + `Tier > Data Type > Match ID > Date` 계층 | 거버넌스 확보, Athena 파티션 프루닝으로 비용 절감, 메달리온 준수 | Prefix 가 길어짐 |
| B. 기존 규칙(0023) 유지 | 변경 없음 | 공용 계정에서 리소스 충돌 |

## 결정

**A 를 채택한다.**

- AWS 리소스 명명 규칙: `{user_id}-{project}-{env}-{region_abbr}-{service}-{tier}-{data}` (예: `{user_id}-lol-dev-an2-kds-brz-chat`)
- S3 데이터 레이크 계층: `s3://bucket/tier/data_type/match_id/yyyy-mm-dd/` (예: `s3://{bucket}/bronze/chat/match_t1_blg_01/2024-11-02/`)
- 설정 파일은 구조 정보(`config.yaml`)와 보안 정보(`.env`)를 분리한다.

## 결과

- 좋아지는 것: 공용 계정 내 리소스 충돌 차단, 특정 경기 분석 시 불필요한 데이터를 읽지 않아 Athena 비용 절감, 새 데이터셋 추가 시 YAML 설정 변경만으로 대응.
- 감수하는 것: 경로(Prefix)가 길어지지만 boto3 등 자동화 스크립트로 해결 가능하다.
- 다시 볼 조건: Athena/Glue 의 파티션 자동 인식이 필요해질 때 (0035 에서 Hive 스타일로 변경).

## 현상

- 프로젝트 초기 단계에서 `MATCH_ID`, `S3_BUCKET_NAME`, `DB_PASSWORD` 등 다양한 설정값들이 소스 코드 내에 하드코딩되어 있음.
- 코드가 복잡해짐에 따라 설정값 하나를 바꿀 때마다 여러 파일의 로직을 수정해야 하는 번거로움이 발생하고, 보안 민감 정보(API Key 등)가 유출될 위험이 있음.
  - **보안 리스크:** DB 비밀번호나 AWS 키가 GitHub 등 코드 저장소에 그대로 노출될 수 있음.
  - **낮은 유지보수성:** 설정 변경 시 매번 코드 전체를 뒤져야 하며, 오타로 인한 런타임 에러 가능성이 높음.
  - **환경 분리의 어려움:** 테스트(Staging) 환경과 실전(Production) 환경의 설정값을 분리하기 어려움.

## 결정

설정의 성격에 따라 **`.env`**와 **`Config 클래스`**의 하이브리드 방식을 채택함.

- **`.env` 파일 사용 (Secret Management):** 보안이 중요한 민감 정보(AWS Key, DB Password)는 서버 로컬 환경의 `.env` 파일에 저장하고 `.gitignore` 처리하여 외부 유출을 차단함.
- **`Config` 클래스 도입 (Centralized Config):** `config.py` 파일을 생성하여 프로젝트 전반에서 쓰이는 공통 설정(버킷 이름, 매치 ID, 프로젝트 버전 등)을 중앙 집중식으로 관리함.
  - `.env`에 저장된 보안 정보도 이 클래스를 통해 접근하도록 일원화함.

## 트레이드오프

- **장점:**
  - **코드 가독성 향상:** 코드 내에서 `Config.MATCH_ID`와 같이 의미 있는 변수명을 사용하여 로직 파악이 쉬워짐.
  - **보안 강화:** 민감 정보가 소스 코드와 분리되어 안전하게 관리됨.
  - **빠른 설정 변경:** `config.py` 파일 한 곳만 수정하면 전체 파이프라인에 즉시 반영됨.
- **단점:**
  - 환경 변수를 로드하기 위한 추가 라이브러리(`python-dotenv`)가 필요하며, 초기 설정 단계가 한 단계 늘어남.

## 배경

프로젝트 초기에 `MATCH_ID`, `S3_BUCKET_NAME`, `DB_PASSWORD` 등이 소스 코드에 하드코딩되어 있었다. 설정 하나를 바꿀 때마다 여러 파일을 수정해야 하고, 민감 정보가 저장소에 노출될 위험이 있으며, Staging/Production 환경 분리가 어렵다.

## 선택지

| 선택지 | 장점 | 단점 |
|---|---|---|
| A. `.env`(비밀) + `Config` 클래스(공통 설정) 하이브리드 | 가독성, 보안 강화, 한 곳만 수정하면 전체 반영 | `python-dotenv` 의존성, 초기 설정 단계 추가 |
| B. 하드코딩 유지 | 없음 | 보안 리스크, 낮은 유지보수성 |

## 결정

**A 를 채택한다.**

- `.env`: AWS Key, DB Password 등 민감 정보를 서버 로컬에 저장하고 `.gitignore` 처리한다.
- `config.py` 의 `Config` 클래스: 버킷 이름, 매치 ID, 버전 등 공통 설정을 중앙 관리하고, `.env` 값도 이 클래스를 통해 접근하도록 일원화한다.

참고로 현업에서는 관리 대상에 따라 `.env`/OS 환경변수(보안, 관리자), Config 클래스(구조, 개발자), Airflow Variables(운영 값, 운영자)로 나누어 관리한다.

## 결과

- 좋아지는 것: `Config.MATCH_ID` 같은 의미 있는 이름으로 로직 파악이 쉽고, 민감 정보가 코드와 분리된다.
- 감수하는 것: 추가 라이브러리와 초기 설정 단계.
- 다시 볼 조건: 운영 중 자주 바뀌는 값이 늘어나 Airflow Variables 같은 별도 관리가 필요해질 때.

# 0038. OpenSearch 서빙 최적화 및 Lambda 전송 안정화 전략

## 현상

- **데이터 정합성 문제:** Flink에서 가공된 '골드 점수'와 '선별 채팅' 데이터를 OpenSearch로 보낼 때, 시간 필드(`ts`, `window_start`)가 날짜(Date) 타입이 아닌 문자열로 인식되어 대시보드 시각화(시계열 그래프)에 어려움을 겪음.
- **람다 전송 실패:** Kinesis에서 OpenSearch로 데이터를 배달하는 람다 함수가 "중간중간" 에러를 뱉으며 멈춤. CloudWatch 로그 분석 결과 `Status: timeout` 발생 확인.
- **비용 및 인프라 제약:** 가성비를 위해 OpenSearch 사양을 낮게(`t3.small`) 잡다 보니 응답 속도가 간헐적으로 느려짐.

## 결정

- **인덱스 템플릿(Index Template) 도입:**
  - OpenSearch에 데이터가 들어오기 전, 미리 '설계도'를 등록하여 인덱스가 생성될 때마다 자동으로 매핑(Mapping)이 적용되게 함.
  - 주석이 제거된 **표준 JSON 형식**의 템플릿 쿼리를 작성하여 Dev Tools 등록 에러 방지.
- **람다 '피지컬' 강화 (Configuration Update):**
  - **제한 시간(Timeout):** `3초` → `30초`로 상향 조정. (OpenSearch의 지연 응답 대기권 확보)
  - **메모리(Memory):** `128MB` → **`256MB`** 이상으로 증설. (파이썬 라이브러리 실행 안정성 확보)
- **리소스 생명주기 관리:**
  - 비용 절감을 위해 OpenSearch, Kinesis, Flink는 작업 종료 후 삭제/중지하되, 비용이 거의 없는 람다는 유지.
  - 익일 재시작 시 [KDS 트리거 갱신]과 [인덱스 템플릿 재등록]을 필수 절차로 정의.

## 이유

- **왜 30초인가?** 타임아웃은 '대기 시간'이 아니라 '최대 허용 시간'임. 1초 만에 끝나면 즉시 종료되므로 실시간성에 영향이 없으며, 인스턴스 사양이 낮아 생기는 간헐적 지연 시 람다가 죽는 것을 방지하는 최소한의 보호 장치임.
- **왜 인덱스 템플릿인가?** 수천 개의 채팅이 쏟아지는 상황에서 인덱스가 바뀔 때마다 수동으로 매핑하는 것은 불가능함. 템플릿을 통해 `date` 타입을 고정해야 Kibana(대시보드)에서 시계열 분석이 가능함.

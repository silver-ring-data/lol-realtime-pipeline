# 0035. 데이터 레이크 S3 경로 설계 및 파티셔닝 전략 채택

> 원본: https://app.notion.com/p/3531198df8d980129444e117db4afdb8

| 채택 | 2026-05-01 |

## 현상

메달리온 아키텍처(Medallion Architecture)를 구현하는 과정에서, S3 내 데이터 저장 경로를 설계할 때 두 가지 접근 방식 사이의 의사결정이 필요했습니다. 특히, 특정 경기(`match_id`)를 최상위 폴더로 둘 것인지, 아니면 데이터의 정제 단계(Layer)와 테이블명(Table)을 최상위로 둘 것인지가 핵심 쟁점이었습니다.

- **대안 1 (Project-centric):** `match_id/layer/table/`
  - 예: `worlds_2024_final/gold/highlight_scores/`
- **대안 2 (Data-centric/Hive Standard):** `layer/table/partition_key=value/`
  - 예: `gold/highlight_scores/match_id=worlds_2024_final/`

## 결정

**대안 2인 '하이브(Hive) 스타일의 파티셔닝 경로'를 최종 채택**합니다. 이는 대규모 데이터 분석 환경(AWS Athena, Spark 등)에서 비용을 최적화하고 성능을 극대화하기 위한 전략적 선택입니다.

## 이유

### 4.1. 쿼리 성능 및 비용 최적화 (Partition Pruning)

- **이유:** 분석 엔진(Athena)이 `WHERE match_id = '...'` 조건을 처리할 때, 대안 2는 관련 없는 데이터를 스캔하지 않고 해당 폴더만 즉시 참조합니다.
- **효과:** 데이터 스캔량이 획기적으로 줄어들어 쿼리 속도가 향상되고 AWS 비용이 절감됩니다. 반면 대안 1은 모든 `match_id` 폴더를 순회해야 하므로 비효율적입니다.

### 4.2. 메달리온 아키텍처의 논리적 격리

- **이유:** `bronze/`, `silver/`, `gold/` 레이어가 최상단에 위치함으로써 각 데이터 정제 단계별로 명확한 경계가 생깁니다.
- **효과:** 단계별 데이터 관리(Lifecycle Policy) 및 보안 권한 관리(IAM Policy)를 적용하기에 훨씬 용이합니다.

### 4.3. 업계 표준 준수 (Best Practice)

- **이유:** `key=value` 형태의 경로는 AWS Athena와 Glue Crawler가 자동으로 파티션을 인식하게 해주는 표준 규격입니다.
- **효과:** 별도의 메타데이터 관리 오버헤드를 줄이고, 현업 수준의 아키텍처임을 증명할 수 있습니다.

## 트레이드오프

- **긍정적 영향:** 데이터 분석 효율 극대화, 인프라 비용 절감, 아키텍처 확장성 확보.
- **부정적 영향:** 사람이 S3 콘솔에서 수동으로 특정 경기의 모든 단계(Bronze~Gold) 데이터를 한 번에 조회하기에는 다소 번거로울 수 있습니다. (하지만 이는 분석 도구를 통해 해결 가능한 영역입니다.)
